# Validation

This document must reflect performed checks, not planned checks. Compilation alone does not establish remote-desktop usability or sustained 4K60 performance.

## Local results (2026-10-09)

Compiled both arm64 applications locally in Debug and Release using Xcode 27.0 on macOS 27.0.1 (build 26A434). Both release bundles are signed with Developer ID Application: Aaron Cousland (5NF98M544G) and pass `codesign --verify --deep --strict`.

The 0.1.1 unrestricted local test run completed **13 passing tests, no skips and no failures**. This includes encrypted/authenticated TLS loopback, rejection of a client with the wrong connection key, delivery of a session rejection before disconnecting, and hardware 3840 × 2160 H.264 encode/decode. The protocol, bounds, geometry, queue-capacity and malformed-video checks also pass. See `.build/test-transparent-mode.log` locally for the exact results.

The 0.1.2 local test run completed **16 passing tests, no skips and no failures**. The additional tests validate live frame-rate/bitrate bounds and compatibility of the extended configuration and desktop messages with older resolution-only messages. See `.build/test-session-controls.log` locally. The separate Session Controls window and live settings handling compile locally in both applications. The controls use an ordinary managed window without full-screen auxiliary or all-Spaces behavior, and open before the viewer's full-screen transition. Live Space switching, focus restoration and capture restart after video-setting changes still need validation on the target Macs.

The 0.1.3 local test run completed **18 passing tests, no skips and no failures**. New checks verify that all ten 16:10 workspaces retain their ratio, fit a 16:10 viewer without letterboxing, and remain within the even-pixel video bounds after HiDPI downsampling. A 3456 × 2160 hardware H.264 encode/decode round trip passes alongside the existing 3840 × 2160 check. See `.build/test-macbook-resolutions.log` locally. The virtual-display bridge now registers both 16:10 and 16:9 modes, and the diagnostic checks required dimensions and 2× backing sizes. A new virtual-monitor diagnostic was not run while the user's existing Screener Server session was active; actual enumeration and live selection of the added modes remain checks for the target pair after restarting the updated Server.

The user subsequently confirmed that the added resolutions are working better, and reported whole-desktop delay over LAN, poor color/quality and local interception of Command–Space, then requested system audio. Source inspection showed the cursor embedded in video, while TCP already had `noDelay` enabled. The final 0.1.4 local run completed **28 passing tests, no skips and no failures**; see `.build/test-session-media.log`. Both apps also compile in Debug; see `.build/build-session-media.log`. The additional coverage includes backward-compatible cursor/audio/video-detail negotiation, latest-frame delivery, decoder cursor-mode transitions with unchanged H.264 parameter sets, and hardware 4K/16:10 encode/decode using the low-latency encoder and reduced decoder buffering. A hardware color-patch round trip validates Rec.709 metadata and pixel values within an eight-level lossy tolerance. Stereo PCM capture-buffer conversion passes for planar and interleaved samples, preserves channel order and rejects malformed/non-finite samples. Audio and video arrive together over authenticated TLS. Shortcut routing excludes inactive apps/Spaces, unavailable desktop images, disabled forwarding and the reserved local controls.

The audio player graph, bounded queues, output-change handling and permission-gated Client event tap compile locally. Live sound output, volume/mute, device switching, event-tap permission acquisition, Command–Space routing and display color comparison have not been exercised on the target pair. Full/Balanced/Fast video settings retain the workspace and aspect ratio in geometry tests; live capture switching and input-to-display latency still need measurement. The responsive local cursor is currently an arrow; embedded mode preserves exact remote shapes. Audio is stereo 48 kHz PCM with a scheduled-buffer limit of 125 ms; movie lip-sync is not implemented.

The user confirmed that 0.1.4 audio plays on both Macs, then requested mini-only speaker suppression, reported mouse-look failure in native The Stanley Parable, and requested the full MacBook panel including the notch strip. The 0.1.5 local run completed **41 passing tests, no skips and no failures**; see `.build/test-game-mouse.log`. Mute ownership/restoration tests cover initially muted devices, output switching, manual overrides, setter failures, disconnected outputs and recovery after relaunch. A separate actual Core Audio check muted and restored this Mac's default output successfully with its original unmuted state restored and volume untouched; see `.build/host-audio-mute-device.log`. Forwarded audio remaining audible while the mini is muted still needs a two-Mac check.

Relative movement tests verify nonzero Core Graphics mouse deltas, fractional accumulation, unaccelerated fields, constant pointer location, drag events and the corresponding Cocoa `NSEvent.deltaX/deltaY` values. Protocol tests validate optional relative input/capability fields and reserve Control–Option–G locally. Local pointer detachment, hiding, focus/Space cleanup and server event posting compile, but live pointer capture and The Stanley Parable camera control have not been tested. Hardware-only raw input paths may ignore injected events.

Full-panel geometry and label tests cover 1512 × 982 and 1728 × 1117 HiDPI workspaces. Hardware H.264 encode/decode passes at 3024 × 1964 and the 16-inch panel's downsampled 3340 × 2160 size. Virtual display settings register both additional modes; a new virtual-display diagnostic is intentionally not run while the user's active Server session owns the monitor. Client opts out of camera safe-area compatibility scaling and Transparent Mode already ignores safe-area padding. Actual mode enumeration and filling the strip beside the notch still require checking on the MacBook. The 2160p stream limit and even-pixel rounding remain.

The rejection regression test failed against the 0.1.0 send-then-cancel behavior: the client received no failure message. It passes after the graceful close fix, including when the server releases its reference to the rejected connection. The user subsequently confirmed that their connection works with 0.1.0; the precise original rejection reason was not established.

Transparent Mode compiles locally in the Client. It hides client chrome in full screen, suppresses local menu/Dock presentation and the duplicate cursor only while the remote desktop is active, and provides Control–Option–T / Control–Option–Esc controls. Live visual validation of full-screen transitions, cursor restoration and the shortcuts on the MacBook remains outstanding.

The runtime diagnostic detected the private display classes and H.264 hardware decode support. A temporary virtual monitor was successfully created, and macOS returned HiDPI workspaces of 1920 × 1080 backed by 3840 × 2160, 2560 × 1440 backed by 5120 × 2880, and 3008 × 1692 backed by 6016 × 3384. The monitor was released when the diagnostic exited. See `.build/virtual-display-local-release.log` locally for the enumerated modes.

Subsequent WindowServer logs show Apple Screen Sharing removing the Screener display due to exclusive display mode and rejecting reuse of that monitor identity. A fresh identity succeeded once, then could not be reused in that session. This occurs with both ad hoc and Developer ID hardened-runtime diagnostics; no signing entitlement failure was established. Automatic recovery from this conflict is not implemented.

Sparkle 2.10.0 is embedded in each app, with separate Server and Client feed URLs. Both apps require signed feeds and verification of update archives before extraction. The existing Ed25519 public identity matches its private seed; the private seed's local directory/file permissions are 0700/0600 respectively, and git ignores all private credentials and build products.

Apple accepted notarization of both release applications. Both bundles have stapled tickets, pass `xcrun stapler validate`, and are accepted by Gatekeeper as Notarized Developer ID. The separate ZIP archives and appcasts are signed and verified with Sparkle's official `sign_update` tool, and the archive SHA-256 checksums match.

The public repository and v0.1.5 preview release are published at https://github.com/acousland/Screener. Both 0.1.5 apps (build 1791522284) were built locally, Developer ID signed, notarized, stapled and accepted by Gatekeeper; see `.build/prepare-release-0.1.5.log`. Both live feeds and their release downloads were fetched without GitHub authentication. Hosted feed signatures, archive signatures, bundle/feed versions, enclosure sizes and SHA-256 checksums all verify against the local release. See `.build/verify-public-0.1.5.log`. Client's prepared bundle also explicitly disables camera safe-area compatibility scaling. The GitHub release is public and not a draft, and GitHub reports Actions disabled with zero workflow runs.

All compilation, tests, signing and release preparation run locally. No GitHub Actions workflows are included. A two-Mac capture/input session, installation of a newer build through Sparkle, and sustained 4K60 performance still require checks on the target pair.

## Automated coverage

- Stream framing across arbitrary packet boundaries, malformed lengths and unknown message types.
- Video packet timestamps, input bounds, letterboxing/coordinate conversion, connection-key parsing, and supported session settings.
- Optional live video settings, rejection of invalid rates, and compatibility with older resolution-only configuration/desktop messages.
- TLS loopback with matching keys, and rejection of a client with the wrong key.
- Delivery of the Server's final error before a rejected connection closes, with the reason preserved on the client.
- Hardware 3840 × 2160 and 3456 × 2160 H.264 encode/decode and rejection of invalid video configurations.
- Preservation of 16:10 geometry through HiDPI downsampling and fitting to a MacBook-shaped viewport.
- Backward-compatible cursor metadata, hardware decoder cursor-mode transitions with unchanged parameter sets, and replacement of stale output waiting for presentation.
- Audio/video-detail compatibility and bounds, stereo PCM capture-buffer conversion and malformed audio rejection, and concurrent audio/video delivery over authenticated TLS.
- Rec.709 H.264 metadata and flat color/gray patch preservation through a hardware round trip.
- Focus, readiness, forwarding preference and reserved-control gating for system shortcut capture.
- Ownership, restoration, route changes, interrupted-run recovery and legacy protocol compatibility for host output muting.
- Relative mouse movement fields and Cocoa deltas, fractional accumulation, pointer input bounds and optional capability negotiation.
- Full-panel MacBook aspect ratios/labels and hardware encode/decode at their network sizes.
- ZIP archive and appcast Ed25519 signature verification during release preparation.

## Two physical Macs

These checks require the M4 mini and M1 Pro MacBook with the necessary macOS permissions:

1. Start the server headless; confirm a virtual monitor appears in Displays.
2. Restart Server 0.1.3 or later and select its virtual monitor. Confirm 16:10 HiDPI modes including 1512 × 945, 1728 × 1080, 1920 × 1200 and 2560 × 1600 appear in macOS and the Client. Switch between these and the existing 16:9 modes; confirm text size changes, the ratio is preserved and video remains within 3840 × 2160. Verify saved scaling survives reopening the Server.
3. Connect/disconnect a physical monitor while streaming. Select either display and verify preserved aspect ratio and input coordinates.
4. Type, drag windows, right-click, double-click, scroll, and use Command shortcuts with at least the normal keyboard layout and trackpad.
5. Hold a key/button while disconnecting and verify the remote desktop is not left with a stuck input state.
6. Test clipboard text in both directions, including the sharing-disabled case.
7. Interrupt the network and verify reconnection, then rotate the server key and verify the old key fails.
8. Measure capture/encode/network/decode latency, frame rate and text quality at 25/45/75/100 Mbps and each video-detail setting. Compare known SDR color swatches and gray ramps with the mini's original display. The current UI reports a target frame rate, not a measured value; HDR/P3 reproduction is not supported.
9. Check Open at Login and behaviour after logout/restart. The server does not provide FileVault or login-window access.
10. Install a newer signed build through each Sparkle feed and verify the correct app is updated with its settings preserved.
11. Enter transparent full screen; confirm Session Controls remains on the regular desktop. Use Control–Option–S, trackpad Space switching and Return to Desktop without leaving full screen or disconnecting. Close/reopen and move the controls to another Space using Mission Control. Check menu/Dock/cursor restoration and absence of stuck keys when focus changes.
12. Change resolution, then apply 30/60 fps and 25/45/75 Mbps from Session Controls. Confirm capture resumes with the requested settings and the same connection. Connect the new Client to an older Server and confirm unsupported live video controls are disabled while resolution controls remain available.
13. Update both apps to 0.1.4 and connect with Responsive Cursor on. Confirm one local arrow moves immediately in normal and transparent full screen, with accurate clicks/drag endpoints. Toggle it during the session and verify only the embedded remote pointer remains when off, including text/resize cursor shapes. Check leaving the viewer, focus changes, disconnects, older-peer fallback and absence of duplicate or missing cursors across capture restarts. Measure desktop reaction latency before/after under the same FPS, bitrate, resolution and LAN conditions.
14. Apply Full/Balanced/Fast video detail and verify the reported stream size changes while the desktop workspace stays the same. Test 16:10, 16:9 and physical portrait displays with input positions correct after each switch.
15. Play stereo sound on the mini and verify left/right channels on the MacBook, volume, stopping/restarting audio, disconnect/reconnect, changing the MacBook's output device and old-server fallback. Confirm turning playback off stops capture, while setting volume to zero mutes the MacBook only. The mini's output volume should stay unchanged. Check Screen & System Audio Recording permission handling and behavior under a slow network. No microphone capture should occur.
16. Grant Accessibility to Client on the MacBook and Server on the mini. With the active remote viewer focused, verify Command–Space opens the mini's Spotlight and Command–Tab stays remote. Confirm local behavior with focus in Session Controls, another app/Space, a disconnected viewer and remote shortcuts off. Verify Control–Option–S/T/Esc remain local, held modifiers release on focus changes, and revoking Accessibility disables interception.
17. With both apps at 0.1.5, stream mini audio with Mute mini speakers on. Verify sound on the MacBook only, then turn off forwarding or disconnect and check original mute state/volume on the mini. Check already-muted outputs, changing outputs, deliberate manual unmuting, capture/playback failures, normal quitting and interrupted-run recovery. Unsupported software-mute outputs must show an error rather than change their volume.
18. Focus native The Stanley Parable on the mini, enable Game Mouse, then click the viewer. Verify continuous camera turning beyond a screen edge, correct horizontal/vertical directions, sensitivity, buttons and scrolling. Turn it off to navigate menus; verify Control–Option–G and Control–Option–Esc release capture, and that focus/Space changes, full-screen transitions, disconnect and quitting restore the local pointer and held inputs. Repeat with any raw-input settings supported by the game.
19. Reopen updated Server, select each 14″/16″ full-screen mode, and enter transparent full screen on the matching MacBook. Confirm content fills the area beside the physical notch and input alignment stays correct. Check existing 16:10 modes still avoid that strip, saved scaling persists, and ordinary desktop controls remain reachable in Session Controls.
